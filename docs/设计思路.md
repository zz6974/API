# 设计思路：每一个文件 & 每一层

> 本文档集中记录项目中**每一个文件**的设计思路（为什么存在 / 关键设计），以及**每一层设计思路存在的意义**。
> 覆盖全部 48 个文件：47 个代码文件（.h/.cpp）+ 1 个构建脚本（CMakeLists.txt）。

---

## 一、每一层设计思路存在的意义

五层六边形架构中，每一层只解决一类问题，层与层之间只能朝一个方向依赖。每一层的设计思路，回答的都是同一个问题：**"这一层为什么必须单独存在？"**

| 层 | 存在的意义 |
|---|---|
| **common 公共层**（5 个文件） | 全项目共享的底层设施（错误处理/日志/配置）。**不依赖任何上层，是其他层的地基。** 没有它，错误码、日志、配置会在各层重复实现。 |
| **domain 领域层**（2 个文件） | 纯领域模型（协议常量/值对象），只描述"是什么"。**不依赖任何层，是全项目的语言字典。** 没有它，协议常量会散落各处，改一个字要改 N 处。 |
| **app 应用层**（10 个文件） | 用例编排业务逻辑；端口接口声明"需要什么能力"而不指定实现。**是依赖倒置的枢纽。** 没有它，业务规则会被协议细节和技术细节淹没。 |
| **web 接口层**（15 个文件） | HTTP 协议与用例之间的翻译器，只做协议转换与响应封装。**不含业务逻辑。** 没有它，HTTP 语义会渗进业务代码，换协议就要重写业务。 |
| **infra 基础设施层**（12 个文件） | 实现 app 层端口；socket/线程/文件/锁等技术细节全部关在这里。**与 web 层同级互不依赖。** 没有它，技术细节会污染所有上层。 |
| **组合根 AppContext**（2 个文件） | 不属于任何层，是唯一知道所有具体类的"粘合点"，五层在此汇聚。**没有它，各层就要互相 new，依赖倒置无从谈起。** |
| **main.cpp** | 进程边界最外层的"壳"，唯一职责是把控制权交给组合根。**没有它，启动逻辑与业务代码混在一起，核心逻辑无法复用。** |
| **CMakeLists.txt** | 构建层——五层静态库的链接依赖在**编译期强制依赖方向**。**没有它，架构规则只存在于文档里，谁反向依赖都编译得过，架构会慢慢腐烂。** |

依赖方向一句话：`common ← domain ← app ← (web | infra) ← 组合根 ← main`，CMakeLists.txt 用静态库链接把这个方向焊死在编译期。

## 二、common 公共层（5 个文件）

### 1. include/api/common/Result.h
- **定位**：统一结果类型 `Result<T>` / `Result<void>`
- **为什么存在**：业务层不抛异常穿越层边界，一切成败以值传递，调用方必须显式处理失败
- **关键设计**：`Ok`/`Fail` 静态工厂强制显式构造；`void` 特化处理无返回值场景；`ValueOr` 提供失败兜底

### 2. include/api/common/ErrorCode.h
- **定位**：全局错误码枚举
- **为什么存在**：把"哪里错了"统一成整数码，成为跨层通用语言，各层不必定义自己的错误表示
- **关键设计**：错误码语义与 HTTP 状态码一一对应，web 层翻译时无需逐业务判断

### 3. include/api/common/Logger.h
- **定位**：日志设施（`LogI`/`LogW`/`LogE` 宏）
- **为什么存在**：统一日志出口，避免各层各写一套打印
- **关键设计**：宏内用 `__func__` 自动记录调用函数名；支持全局日志级别开关

### 4. include/api/common/Config.h
- **定位**：`ServerConfig` 配置结构（声明）
- **为什么存在**：集中全部端口/路径配置字段，作为唯一配置入口传给组合根
- **关键设计**：配置以值注入而非全局变量读取，便于测试与替换

### 5. src/api/common/Config.cpp
- **定位**：配置加载实现
- **为什么存在**：把 JSON 解析集中在一处，其余代码只拿配置值，不碰解析细节
- **关键设计**：逐字段读取、缺字段保留默认值；解析失败返回 `Fail` 而非抛异常

## 三、domain 领域层（2 个文件）

### 6. include/api/domain/Protocol.h
- **定位**：协议常量（命令前缀等）
- **为什么存在**：终端与服务器共享的语言字典，纯常量无逻辑，改协议只动这一处
- **关键设计**：namespace 隔离，零依赖，任何层都可安全引用

### 7. include/api/domain/PhotoMeta.h
- **定位**：照片元数据值对象
- **为什么存在**：把"一张照片是什么"（id/大小/时间）固化成类型，比散装的裸字段更有约束力
- **关键设计**：只描述不做事，无任何依赖，纯值语义可自由拷贝

## 四、app 应用层（10 个文件）

### 端口接口（4 个，依赖倒置的枢纽）

### 8. include/api/app/port/ICameraChannel.h
- **定位**：单条摄像头 TCP 通道的端口接口
- **为什么存在**：把"一条通道能干什么"抽象成最小契约，业务层不关心底层 socket 细节
- **关键设计**：纯虚接口、零依赖；实现（`TcpCameraChannel`）留在 infra 层，实现依赖倒置

### 9. include/api/app/port/ICameraChannelManager.h
- **定位**：摄像头通道池的端口接口
- **为什么存在**：抽象"管理一群通道"的能力（启动/停止/查找），上层不碰线程与 socket
- **关键设计**：`Find` 返回 `shared_ptr` 规避裸指针悬垂风险；实现（`CameraChannelManager`）留在 infra 层

### 10. include/api/app/port/IIdAllocator.h
- **定位**：设备 ID 分配器的端口接口
- **为什么存在**：抽象设备号分配策略，便于替换实现（槽位式/数据库自增等）
- **关键设计**：`Allocate` 返回 `Result`，池满以错误码表达而非异常；实现（`SlotIdAllocator`）留在 infra 层

### 11. include/api/app/port/IPhotoRepository.h
- **定位**：照片持久化的端口接口
- **为什么存在**：抽象存储位置（文件/数据库），业务层只要求存/取/列三种能力
- **关键设计**：`Save` 返回 `photoId` 作为后续取照片的句柄；实现（`FilePhotoRepository`）留在 infra 层

### 用例服务（6 个）

### 12. include/api/app/service/AuthService.h
- **定位**：认证用例服务（声明）
- **为什么存在**：账号密码校验独立成用例，供 web 层 AuthController 调用
- **关键设计**：校验逻辑集中在服务内，将来可替换为数据库比对/加盐哈希而不动调用方

### 13. src/api/app/service/AuthService.cpp
- **定位**：认证用例实现
- **为什么存在**：校验流程落地（参数判空→比对），保持服务接口稳定
- **关键设计**：失败以 `Result` + 错误码表达，不向调用方抛异常

### 14. include/api/app/service/CameraService.h
- **定位**：摄像头用例服务（声明）
- **为什么存在**：把"设备注册/状态查询/拍照"编排成用例，控制器只做协议翻译
- **关键设计**：依赖端口接口而非具体类，业务规则集中于此

### 15. src/api/app/service/CameraService.cpp
- **定位**：摄像头用例实现
- **为什么存在**：用例流程落地（参数校验→委托仓库）
- **关键设计**：参数校验前置，非法请求不进入仓库层；错误码直接透传

### 16. include/api/app/service/PhotoService.h
- **定位**：照片用例服务（声明）
- **为什么存在**：拍照片/取照片的用例独立成服务，隔离 web 与持久化细节
- **关键设计**：通过 `IPhotoRepository` 端口访问存储，可替换实现

### 17. src/api/app/service/PhotoService.cpp
- **定位**：照片用例实现
- **为什么存在**：照片存取流程落地（生成→保存→查询）
- **关键设计**：`photoId` 贯穿存与取，业务不感知文件路径等细节

## 五、web 接口层（15 个文件）

### HTTP 基础设施（7 个）

### 18. include/api/web/http/HttpTypes.h
- **定位**：HTTP 类型定义（请求/响应结构）
- **为什么存在**：请求响应数据结构集中定义，各控制器共享同一套类型
- **关键设计**：纯数据结构，无业务逻辑

### 19. include/api/web/http/Router.h
- **定位**：路由表（声明）
- **为什么存在**：把"路径模式 → 处理器"的注册与匹配抽象出来，控制器无需关心匹配细节
- **关键设计**：支持 `{id}` 占位符模式，注册时声明参数名

### 20. src/api/web/http/Router.cpp
- **定位**：路由匹配实现
- **为什么存在**：把模式字符串的切段、匹配、占位符抓取集中在一处
- **关键设计**：路径按 `/` 切段，字面量段相等才命中，`{id}` 段抓取参数名与值；匹配失败返回 false

### 21. include/api/web/http/BaseController.h
- **定位**：控制器基类（声明）
- **为什么存在**：把响应封装与错误码→HTTP 状态码映射下沉到基类，控制器只写业务调用
- **关键设计**：JSON 解析失败统一回参数错误，映射表集中维护

### 22. src/api/web/http/BaseController.cpp
- **定位**：控制器基类实现
- **为什么存在**：响应封装与错误码映射的落地
- **关键设计**：错误码→HTTP 状态码映射表集中一处，新增错误码只改这里

### 23. include/api/web/http/HttpServer.h
- **定位**：HTTP 服务器封装（声明）
- **为什么存在**：把 SDK 回调与路由框架对接起来，控制器不感知底层 HTTP 库
- **关键设计**：初始化与运行分离，便于 AppContext 控制启动时机

### 24. src/api/web/http/HttpServer.cpp
- **定位**：HTTP 服务器封装实现
- **为什么存在**：SDK 回调与路由框架的对接点
- **关键设计**：路由未命中统一回 404；请求分发全部走 Router

### 控制器（8 个）

### 25. include/api/web/controller/AuthController.h
- **定位**：认证控制器（声明）
- **为什么存在**：`/api/login` 路由的协议翻译入口
- **关键设计**：只做解析→调用服务→封装响应，不含校验逻辑

### 26. src/api/web/controller/AuthController.cpp

- **为什么存在**：`/api/login` 路由落地（解析 POST 体→校验→响应）

### 27. include/api/web/controller/CameraController.h
- **定位**：摄像头资源控制器（声明）
- **为什么存在**：`/api/camera/*` 路由的协议翻译入口
- **关键设计**：只依赖 CameraService 用例，不含业务规则

### 28. src/api/web/controller/CameraController.cpp
- **定位**：摄像头资源控制器实现
- **为什么存在**：`/api/camera/*` 路由落地（参数校验→调用用例→Result 转 HTTP 响应）
- **关键设计**：非法设备 ID 统一 400；拍照成功回传元信息，照片本体走 `/api/photo/{photoId}`

### 29. include/api/web/controller/PhotoController.h

### 30. src/api/web/controller/PhotoController.cpp
- **定位**：照片资源控制器实现
- **为什么存在**：`/api/photo/*` 路由落地（参数校验→调用用例→响应）
- **关键设计**：`photoId` 判空前置；照片本体以 JPEG 二进制回传

### 31. include/api/web/controller/IdController.h

### 32. src/api/web/controller/IdController.cpp

## 六、infra 基础设施层（12 个文件）

### 网络（8 个）

### 33. include/api/infra/net/TcpCameraChannel.h
- **定位**：单条摄像头 TCP 通道（声明）
- **为什么存在**：实现 `app::ICameraChannel` 端口，摄像头长连接的一切协议细节关在这里
- **关键设计**：行/二进制双模式状态机；ID 分配由注入的 `IIdAllocator` 提供；`TakePhoto` 返回 `Result<vector<char>>`

### 34. src/api/infra/net/TcpCameraChannel.cpp
- **定位**：单条摄像头 TCP 通道实现
- **为什么存在**：协议解析与帧/照片收发的落地
- **关键设计**：`RecvLoop` 逐字节状态机（行模式攒到 `\n`；二进制按声明长度吞字节）；`ProcessLine` 按前缀分发；拍照用带谓词的定时等待

### 35. include/api/infra/net/CameraChannelManager.h
- **定位**：摄像头通道池（声明）
- **为什么存在**：实现 `app::ICameraChannelManager` 端口，管理 TCP 监听与全部会话
- **关键设计**：`sessions_` 存 `shared_ptr`；`shared_mutex` 读写分离保护

### 36. src/api/infra/net/CameraChannelManager.cpp
- **定位**：摄像头通道池实现
- **为什么存在**：TCP 监听与会话生命周期管理的落地
- **关键设计**：`accept` 循环 + 注册等待超时；`Stop` 时先关开关/监听、再回收线程、最后归还全部 ID

### 37. include/api/infra/net/UdpHeartbeatService.h
- **定位**：UDP 心跳服务（声明）
- **为什么存在**：落地 UDP 广播心跳 + ACK 打洞，让终端与服务器互相发现
- **关键设计**：固定布局报文按字节序对齐；收发双线程；地址端口由 `Start` 参数传入不硬编码

### 38. src/api/infra/net/UdpHeartbeatService.cpp
- **定位**：UDP 心跳服务实现
- **为什么存在**：心跳广播、ACK 等待、RTT 统计的落地
- **关键设计**：`SendLoop` 广播后等 3 秒 ACK 完成打洞；`RecvLoop` 过滤 ACK 只处理终端心跳；`steady_clock` 单调测 RTT

### 39. include/api/infra/net/WebSocketStreamService.h
- **定位**：WebSocket 推流服务（声明）
- **为什么存在**：在独立端口向前端持续推送摄像头实时帧的旁路推流通道
- **关键设计**：推流循环与主业务隔离，断连自动退出

### 40. src/api/infra/net/WebSocketStreamService.cpp
- **定位**：WebSocket 推流服务实现
- **为什么存在**：推流循环的落地（查在线→取帧→二进制发送）
- **关键设计**：无设备慢速空转、无帧快速重试的两档轮询；连接断开自动退出循环

### 存储（2 个）

### 41. include/api/infra/persistence/FilePhotoRepository.h
- **定位**：文件照片存储（声明）
- **为什么存在**：实现 `IPhotoRepository` 端口，把照片以文件形式落盘
- **关键设计**：文件名即 `photoId`，与业务层解耦；`shared_mutex` 写独占/读共享保护目录

### 42. src/api/infra/persistence/FilePhotoRepository.cpp
- **定位**：文件照片存储实现
- **为什么存在**：照片存/取/列的落地
- **关键设计**：毫秒时间戳+随机串命名防碰撞；Win32/POSIX 双实现枚举目录；写盘独占锁防并发读写目录

### ID 分配（2 个）

### 43. include/api/infra/id/SlotIdAllocator.h
- **定位**：槽位式 ID 分配器（声明）
- **为什么存在**：实现 `IIdAllocator` 端口，设备号分配策略的落地
- **关键设计**：`vector<bool>` 槽位表，下标即设备号

### 44. src/api/infra/id/SlotIdAllocator.cpp
- **定位**：槽位式 ID 分配器实现
- **为什么存在**：分配/归还/查询槽位的落地
- **关键设计**：线性扫第一个空槽（容量小无需优化）；越界 ID 静默忽略；全满回 `kNoIdAvailable`

## 七、组合根与进程入口（4 个文件）

### 45. include/api/AppContext.h
- **定位**：组合根（声明）
- **为什么存在**：五层架构中唯一知道所有具体类的地方，负责依赖注入装配与生命周期管理
- **关键设计**：只依赖端口与具体类，各层互不感知；`Router` 先于 `HttpServer` 构造，保证生命周期最长；`Shutdown` 可重复调用

### 46. src/api/AppContext.cpp
- **定位**：组合根实现
- **为什么存在**：把"谁依赖谁、谁先启动谁先停止"的装配逻辑集中在一处，业务代码零感知
- **关键设计**：`Init` 按依赖方向装配（infra → app → web）；`Shutdown` 逆序停止；config 注入而非读全局

### 47. src/main.cpp
- **定位**：进程入口
- **为什么存在**：把可执行程序与库代码分隔，让核心逻辑可测试、可复用
- **关键设计**：设日志级别 → 加载配置 → 装配 AppContext → 阻塞运行，四步即全部职责，不含任何业务逻辑

### 48. CMakeLists.txt
- **定位**：构建脚本
- **为什么存在**：把五层编译成独立静态库，用链接依赖在编译期强制依赖方向，谁反向依赖谁编译不过
- **关键设计**：`api_domain` 是 INTERFACE 库（纯头文件无编译产物）；`API` 可执行文件只链接组合根（main.cpp + AppContext.cpp），其余全部通过静态库传递
